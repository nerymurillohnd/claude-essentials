# Issues use forms and a triage flow; labels are a prefixed taxonomy kept as code

## Context and Problem Statement

A public marketplace receives bug reports, feature requests, plugin
proposals, and questions about many independent plugins. GitHub's defaults
don't identify which plugin an issue concerns: blank issues and ten unscoped
labels. Issue types need an organization, and this repository belongs to a
user account. Issue forms silently drop labels that don't exist. PRs from
forks get read-only tokens, so labeling them needs `pull_request_target`,
which is dangerous if misused. How should issues be collected and triaged,
and how should issues and PRs be labeled?

## Decision Drivers

- Every issue arrives classified (type, plugin) with the facts needed to act.
- Labels can't drift between code, forms, and GitHub.
- Automation must never execute untrusted PR code with a write token.
- Keep the maintainer's triage load low; no silent auto-closing of real work.

## Considered Options

- Issue forms, a prefixed taxonomy in `.github/labels.json` synced by a
  script, and a first-party triage script
- Issue forms plus third-party label and labeler actions
- GitHub defaults with manual labeling

## Decision Outcome

Chosen option: "Issue forms, a taxonomy as code, and a first-party triage
script".

- Forms: bug report, feature request, plugin proposal, and documentation
  problem. Blank issues are disabled. Questions go to Discussions Q&A,
  vulnerabilities to private advisories, and Claude Code bugs upstream. The
  **Affected plugin** dropdown is generated by `npm run generate`, and CI
  fails if it's stale.
- Taxonomy: the `type:`, `status:`, `priority:`, `area:`, `plugin:` (derived),
  and `bump:` families, plus `good first issue` and `help wanted`
  ([labels.md](../contributing/labels.md)). `npm run validate` checks names,
  lengths, and colors, that every label automation needs exists, that every
  form label exists, and that no alias equals any label name or is shared by
  two labels.
- Sync: `scripts/sync-labels.mjs` is a dry run by default. The `Labels`
  workflow applies it on merge but never prunes. Default labels map to the
  new names through `aliases`, so renaming keeps their associations.
- Triage (`scripts/triage.mjs`, `triage.yml`):
  - issues get `plugin:` or `area: catalog` from the dropdown;
  - an author's reply to a `needs-info` issue moves it back to triage;
  - PRs get `area:`, `plugin:`, and a computed `bump:` label from the same
    rules as `version-check` (ADR-0003). A PR-derived `plugin:` label is only
    created for a name matching the plugin-name rule
    (`^[a-z0-9]+(-[a-z0-9]+)*$`, ≤ 42 characters); anything else is left
    unlabeled rather than creating an invalid label.
  The workflow checks out the base branch only, installs without scripts or a
  cache, and reads PR content through the API as data. Its concurrency group
  is scoped by event name, so an issue comment (`needs-info` reply) can't
  cancel a PR's in-flight labeling run.
- Stale: only `status: needs-info` issues, stale after 14 days, closed as
  *not planned* 7 days later.
- Resolution uses GitHub's native close reasons, not labels.

### Consequences

- Good, because every issue and PR is classified without manual work, and
  labels can't reference things that don't exist.
- Good, because first-party scripts reuse the version rules and avoid
  third-party supply-chain exposure in a job that holds a write token.
- Bad, because the triage and sync scripts are code this repo has to maintain.
- Bad, because a new plugin's label is created with a placeholder
  description until the `Labels` workflow runs after merge.
- Neutral: labels applied by hand in the GitHub UI still work, but the next
  sync overwrites their color and description.

### Risks and mitigations

| Risk | Likelihood or condition | Impact | Mitigation or response | Owner |
| --- | --- | --- | --- | --- |
| A future edit checks out the PR head in `triage.yml` | Contributor or maintainer error | Arbitrary code runs with a write token | SECURITY comments in the workflow; review any change to `triage.yml` as security-sensitive | Maintainer |
| GitHub changes how issue-form answers render (`### Label`) | Platform change | Plugin labels stop being applied to issues | Unit test pins the format; the triage log shows no labels added | Maintainer |

| Pruning deletes a label still in use | Manual `--prune` | Labels vanish from issues | Pruning is manual, previewed as a dry run, and never run by CI | Maintainer |

### Amendment — 2026-09-18: surface-aware forms, schema validation, native controls reused

- **Forms follow the plugin contract.**
  - The bug report adds required **Surface** (Claude Code or Claude Cowork) and **Installed from** fields; local-checkout installs are marked unsupported, per the root README's support policy. It also adds an optional regression question, the last working version, and an `upload` element for logs and screenshots.
  - The plugin proposal adds target surfaces, external requirements, trigger and non-trigger examples (future eval cases), a public-safety checkbox, and an Apache-2.0 contribution statement.
  - The feature request adds an optional surface field.
  - The `Affected plugin` field, its options, and every existing field `id` are unchanged, so the generator and the triage bot are unaffected.
- **Structure is validated, not just labels.** GitHub publishes no schema for issue forms, so `schemas/github/` vendors SchemaStore's `github-issue-forms` and `github-issue-config` schemas, unmodified except for an added `$comment` with source and date. `npm run validate` checks every form and `config.yml` against them.
- **Native platform features were checked before building anything** (2026-09-18):
  - PR forms don't exist, so the PR template stays Markdown.
  - Issue types remain unavailable for a user-owned repository: GraphQL returns `issueTypes: null` here, while `anthropics/claude-code` returns Task, Bug, and Feature. The `type:` labels stay.
  - GitHub's own secret scanning, push protection, and private vulnerability reporting are enabled.
  - `delete_branch_on_merge` is enabled.
